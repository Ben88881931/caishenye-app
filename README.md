线上地址：https://ben88881931.github.io/caishenye-app/

## 当前架构

这是一个静态单页应用（SPA）。入口是根目录的 `index.html`，主逻辑在 `app.js`，样式在 `styles.css`，开奖数据由根目录 `data.js` 提供。

旧版多页面已经迁移到 `legacy/`，不再作为主入口，仅保留备份和兼容用途。

## 数据流

1. `lottery_data.json`：所有期数的尾数二进制。键是期数字符串，值是 10 位 `0/1` 字符串，第 i 位表示尾数 i 本期是否开出。
2. `号码走势图.html`：每期 7 个完整号码、生肖、太岁，以 `var D=[...]` 形式保存，是号码/生肖相关页面的数据来源。
3. `sync.py`：读取上面两个文件，生成根目录 `data.js`，内容为 `window.APP_DATA = { raw, d }`。
4. `app.js` 启动时读取 `window.APP_DATA`，把所有页面渲染成 SPA 标签页。

GitHub Actions（`.github/workflows/sync-v2.yml`）会在 push、每日定时和手动触发时运行 `sync.py`，如果 `data.js` 变化就自动提交。

## 主页面标签

当前 `app.js` 的 `TABS` 包含：

总览、尾号性格、分段对比、窗口走势、遗漏热图、遗漏排序、单双热图、下期预估、双号推荐、调度模型、追号模型、追推荐模型、三期规律、遗漏监控、冷热分析、策略回测、生肖开奖、生肖窗口、生肖遗漏、号码走势、生肖走势、下单记录。

导航采用两级分类，所有页面分配到以下分类，不直接堆在一条导航上：

- 推荐下单：下期预估、双号推荐、调度模型、追号模型、追推荐模型、下单记录。
- 走势总览：总览、分段对比、窗口走势、号码走势、生肖走势。
- 遗漏分析：遗漏热图、遗漏监控、遗漏排序、单双热图。
- 生肖专区：生肖开奖、生肖窗口、生肖遗漏。
- 分析工具：尾号性格、三期规律、冷热分析、策略回测。

导航支持本机自定义：

- 一级分类可用箭头上下调整顺序。
- 一级分类可折叠和展开，折叠状态会保留。
- 第二级页面可用箭头在当前分类内上下调整。
- 排序模式下，每个页面可通过“移动”菜单跨分类调整。

主要页面含义：

- 遗漏热图：按尾数 `0-9` 正常排列，红=开出，蓝=遗漏1期，绿=遗漏2期，黄=遗漏3期及以上并写遗漏期数。
- 遗漏排序：列不按数字大小排列，而是按每个尾数最近一次“连续遗漏满 3 期及以上”的时间排序，旧的靠左，最新发生的靠右。
- 单双热图：奇数尾数放左，偶数尾数放右；左右两侧内部仍按遗漏排序规则排列。
- 分段对比：窗口为 `5 / 7 / 10 / 15 / 21 / 30`，包含最近三段对比和历史分段表。上一段满期后会自动追加“下一段未开”提示。
- 尾数滚动开出率：显示所选尾数的滚动开出率曲线，红点表示该尾数实际开出的期数。
- 生肖开奖：底部包含生肖分布统计。
- 尾号性格：包含遗漏反弹性格表、连出性格表、当下状态表。
- 窗口走势：每个尾号可查看各窗口每期上下浮动线。
- 双号推荐：连出惯性分层打分，每期给出D1首推和D2备选。
- 调度模型：监控双号追热与加权追冷的对错、遗漏、连中和相位，输出跟双号、跟加权或观望。
- 追号模型：锁定一个起始推荐号码固定追3期，同一位置同时只跑一条追号线。
- 追推荐模型：每期新推荐独立追3期，允许不同推荐并行运行。
- 下单记录：统一记录追号和追推荐的下单、结算状态和净收益，不再保留重复的下单追投页面。本金、号码、模式和倍投由用户手动决定，开奖数据齐全后自动判断第1/2/3期中或三期全错。
- 追中记录：不单独占一级页面，直接显示在追号模型和追推荐模型底部，只展示对应模式的命中记录，并标记在第1期、第2期还是第3期中。
- 总览：顶部固定展示“每日选号下单顺序”，按“调度模型 → 首推置信率 → 追号/追推荐 → P档 → 下单记录 → 自动结算”的流程操作。

## 号码和生肖规则

- 号码颜色：
  - 红波：`1,2,7,8,12,13,18,19,23,24,29,30,34,35,40,45,46`
  - 蓝波：`3,4,9,10,14,15,20,25,26,31,36,37,41,42,47,48`
  - 其余为绿波。
- 生肖顺序：`鼠、牛、虎、兔、龙、蛇、马、羊、猴、鸡、狗、猪`。
- 生肖映射：号码 `N` 的生肖 = `ZODIACS[(6 - (N - 1)) % 12]`，其中 6 是 2026 年太岁“马”的索引。跨年份时以当年太岁为准，页面直接使用 `D` 中的 `tai` 和 `zods` 字段，不需要重新推算。

## 每日更新标准操作

用户提供最新一期开奖号码后，在仓库根目录执行：

```bash
python update_daily.py <期数> <7个号码>
```

例如：

```bash
python update_daily.py 236 25,30,37,19,07,17,39
```

然后重新生成 SPA 使用的 `data.js`：

```bash
python sync.py
```

最后提交并推送：

```bash
git add -A
git commit -m "更新第236期数据"
git push origin main
```

注意事项：

- 只更新用户实际提供的号码，不自行猜测或补造号码。
- 更新后确认 `data.js` 已生成，且最新期数正确。
- 如果 `app.js` / `styles.css` 没有改动，就不要修改它们。
- 旧版 `legacy/` 页面可以同步更新，但不需要作为主入口维护。
- 如果用户当天没发号码，不要写假数据；可先运行 `python sync.py` 确认现有数据已经同步。

## 每日自检与预测逻辑维护

每天更新后，除了确认最新数据，还要运行：

```bash
node page_audit.js
python check_app.py
node --check app.js
```

`check_app.py` 会检查：

- 期数是否连续、尾数二进制是否为 10 位 `0/1`。
- `号码走势图.html` 的 7 个号码和生肖是否完整。
- `data.js` 是否与 `lottery_data.json`、`号码走势图.html` 一致。
- `app.js` 语法是否正常。
- 关键预测函数是否存在。

预测逻辑重点关注：

- 不要在有并列最高分时强行推荐单一尾数，宁可提示“信号接近，建议跳过”。
- 推荐结果要显示历史反弹率和样本量，样本不足时要明确标注。
- 不使用未开奖号码，不做伪造数据。
- 每次改动后都要重新运行自检，通过后再提交。

## 模型监督与真实快照

从当前版本开始，预测模型统一放在 `model_core.js`，页面和监督脚本共用同一份算法。

每次更新开奖号码前先运行：

```bash
node model_supervisor.js sync
```

这会先保存下一期预测快照。更新数据并运行 `python sync.py` 后，再次运行：

```bash
node model_supervisor.js sync
```

已开奖快照会被结算为真实对/错，保存到 `prediction_snapshots.json`。

查看真实快照战绩：

```bash
node model_supervisor.js report
```

完整的下属执行和监督规则见 `SUPERVISOR_WORKFLOW.md`。

## 双号追号与追推荐模型

`ultimate_model.js` 是统一的双号推荐监控与追投研究模块，`ultimate_backtest.js` 是命令行回测入口。该模块只读取双号推荐 `D1/D2`，不读取下期预估 `W1/W2`。

模式差异：

- **追号模式**：每一批锁定起始推荐号码，固定追3期；追号期间新出的推荐不参与，命中或3期结束才开下一批。
- **追推荐模式**：每期新出的推荐都单独开始一批3期追号，旧批未结束时允许并行，因此同一期可能有多条追号线。

每次代码或数据更新后运行：

```bash
node ultimate_backtest.js
```

该命令同时执行固定结算用例自检，覆盖第1期中、第2期中、三期全错和数据未齐保持待开奖。

当前规则版本为 `ultimate-v1`：

- 每个推荐位置独立追3期，中一次立即结束，三期全错止损。
- 状态分数由近10/20/50期命中率、理论基准差、当前遗漏分位、当前连中和当前连错共同计算。
- 低于35分：观望。
- 35至59分：使用P6 `1 / 1.25 / 2.8125` 保本追投。
- 60至79分：使用P7 `1 / 1.5 / 3.375` 收益型追投。
- 80分及以上：使用P8 `1 / 3 / 9` 激进追投。
- 状态分数只使用当下之前的数据，回测不使用未来数据。

两个模型当前都是实验规则。真实快照不足100期时，只展示监控和回测结果，不作为稳定盈利承诺。下单记录与模型内追中记录使用浏览器 `localStorage`，每台设备的数据相互独立。

自动结算规则：

- 只处理状态为“待开奖”的记录，不覆盖已经人工或自动结算的记录。
- 从起始期开始依次检查3期。
- 第1期中记`hit1`，第2期中记`hit2`，第3期中记`hit3`。
- 三期都没有该尾号时自动记为`miss`。
- 起始期之后的数据还没开完时保持待开奖。
- 自动结算记录显示“自动”，并同步进入对应模型的追中记录。

旧“下单追投”页面及其死代码已移除，仓库只保留新的“下单记录”作为唯一下单入口。

## 第四套调度模型

`model_selector.js` 和 `selector_backtest.js` 构成第四套模型。第四套不预测号码，只预测两套推荐模型的正确/错误相位，调度目标是选择更可能正确的推荐流。

运行：

```bash
node selector_backtest.js
```

当前规则 `selector-v1`：

- D1、D2、W1、W2分别建立独立对错序列，单独计算下一期正确概率、状态样本和置信档，不共用一套分数。
- 双号首推达到A级及以上，且加权反弹率≥65%，允许跟双号。
- 双号首推连续错2期时，暂停跟双号。
- 双号备选连续命中3期后，暂停双号确认。
- 加权首推对错遗漏达到2期，或刚刚连续命中1期，允许观察跟加权。
- 加权备选连续错2期时，不跟随加权。
- 加权空推荐且双号未确认时，观望。
- 推荐尾号实际连出≥5期时禁止追热。

独立置信率按“当前对错连续状态”的历史条件概率计算，再用整体正确率做平滑：

```text
下一期正确概率 =（该状态历史命中 + 基础正确率×5）/（该状态样本 + 5）
```

页面同时展示正确概率、置信度、状态样本、基础正确率和优先/观察/避让建议。独立置信属于辅助信息，最终调度动作仍以P1-P6规则为准。

调度页面同时展示“三期内命中结构”：按调度选中的模型首推号，锁定追3期，统计第1期中、第2期中、第3期中、三期全错和双号/加权来源。该统计与单期调度回测分开。

追号模型和追推荐模型页面的三期内追投记录统一从第31期起，每批明确标注起始期、锁定尾号、逐期实际检查的期数和号码、每期中/错以及结束期。

追号模型和追推荐模型页面顶部新增“本期锁定号”卡片，直接给出下一期 D1/D2 的候选尾号、等级分数、信号标签、当前强弱、建议P档和追三期范围。追号模式提示未结束前不换号；追推荐模式提示本期新增推荐线并允许并行。只有状态为强或稳的候选才显示“锁定”，弱状态显示“不锁”；两条都弱时显示“本期不建议锁定”。锁定卡主视觉固定使用高显眼绿色；如果总调度为观望，必须在绿色卡内显示橙色提示条“只观察，不产生订单”。最终下单仍服从总览调度层。

追号模型和追推荐模型顶部卡片内部顺序固定为：锁定信息、三期内追投滚动记录、最近推荐监控、追中记录；当前决策保留在卡片之后。调度模型顺序为：最终动作、三期内必出滚动记录。记录区必须在生成 HTML 时紧接放在卡片下方，不得嵌套进卡片，也不得依赖渲染后搬移节点；页面下方不得重复展示。

顶部导航使用粘性定位，应用标题随页面滚走但导航保留在顶部。五个一级分类固定为等宽分段按钮；点击当前分类折叠或展开，点击其他分类直接进入其第一个页面。二级页面横向位置在重渲染后保持，当前页自动滚动到可见区域；切换页面时内容回到顶部。

四条推荐流另有独立的“三期内必出”统计：D1、D2、W1、W2分别锁定各自首推号追3期。页面下方提供一条横向滚动记录，每一格显示起始期、锁定号码，以及第1/2/3期分别检查了哪一期、哪个号码、是中是错；支持全部、D1、D2、W1、W2筛选。

第四套页面只做调度监控和影子记录，不自动下单，不自动资金分配。

## 双号推荐五级强度与命中率统计

双号推荐（连出惯性分层打分，每期推 2 个尾号）新增五级强度分级，等级规则统一定义在 `model_core.js` 的 `gradeOf` / `GRADE_TIERS`，禁止页面/监督脚本/统计脚本各算一套：

- S 级：分数 ≥ 95.0
- A 级：93.5 - 94.99
- B 级：92.8 - 93.49
- C 级：92.2 - 92.79
- D 级：< 92.2

每次结算后，`model_supervisor.js` 会自动生成 `snapshots.js`（`window.APP_SNAPSHOTS`），页面据此展示：

- **逐期对错**：每个已结算快照记录推荐尾号、分数、等级、实际尾数、逐尾号命中、双号是否至少中一、结算时间。
- **单尾命中率**：每个推荐尾号按自己的等级分组统计命中数/样本数。
- **双号整体至少中一**：全部已结算快照（不分等级）统计至少命中一个的命中数/期数。
- **等级组合至少中一**：按两个推荐尾号的等级组合（如 A+C、C+C、C+D）分组统计至少命中一个的命中数/样本数。

所有统计样本少于 20 期时显示「样本不足」，不作命中率结论。数据只来自真实快照账（`prediction_snapshots.json`），与回测账严格分开，不做数据美化。

运行统计脚本：

```bash
node score_calibration.js report
```

前端缓存版本：`index.html` 里的 `data.js` / `model_core.js` / `model_selector.js` / `ultimate_model.js` / `snapshots.js` / `app.js` / `styles.css` 使用统一构建版本号（如 `?v=20260928-31`），以上文件内容变化时必须同步更新版本号，否则浏览器可能读到旧缓存。
